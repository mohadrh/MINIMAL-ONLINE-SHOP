# موتور قیمت، تخفیف و تحویل خودکار — نقشه‌ی کار

این سند ساختارِ کارِ خواسته‌شده است، تا در طولِ ساخت چیزی گم نشود.
هر بخش یک شماره دارد؛ وقتی تمام شد، همین‌جا تیک می‌خورد.

## وضعیت

| بخش | وضعیت |
|---|---|
| ۱ نرخ تتر از چند منبع | ✅ ساخته شد |
| ۲ تازه‌سازی ساعتی + سرِ خرید | ✅ ساخته شد |
| ۳ پنل وردپرس | ✅ ساخته شد — شش صفحه |
| ۴ خریدِ خودکار | ⏸ صف و پنلش ساخته شد، خودِ خرید عمداً خاموش |
| ۵ تخفیف‌ها | ✅ ساخته شد |
| ۶ امنیت و تست | ✅ ۵۸ تست، همه قبول |

**فایل‌ها:**

```
wp-plugin/phoenix-bridge/
  includes/
    db.php               جدول‌ها، تنظیمات، دفترِ رویداد
    rate-sources.php     چهار صرافی + منبعِ سفارشی
    rate.php             جمع‌آوری، فیلترِ پرت، انتخاب، کش، اندپوینت
    pricing.php          قیمتِ تمام‌شده → حاشیه → رُند → کف → نوشتن
    discounts.php        قاعده‌های گروهی + کدِ اختصاصی
    product-pricing.php  فیلدها روی صفحه‌ی محصولِ ووکامرس
    fulfil-queue.php     صفِ تحویل
    admin/               شش صفحه‌ی پنل
  assets/admin.css
wp-plugin/tests/pricing-test.php   ← npm run test:pricing
```

⚠ **چیزی که هنوز تست نشده:** همه‌ی این‌ها روی وردپرسِ واقعی نصب
نشده‌اند، چون وردپرسی هنوز بالا نیست. منطقِ ریاضی با تست پوشش
دارد؛ نوشتنِ قیمت روی محصول، قفلِ سبد، و خودِ پنل باید روی نصبِ
واقعی دیده شوند.

---

## ۰ — پیش‌نیازها که دستِ ماست نیست

بدون این‌ها هیچ‌کدام از بخش‌های زیر واقعاً کار نمی‌کند:

| چه چیزی | چرا لازم است | وضعیت |
|---|---|---|
| وردپرس بالا و در دسترس | همه‌ی این‌ها افزونه‌ی وردپرس است | ❌ هنوز نه |
| ووکامرس فعال | سفارش، کوپن، محصول | ❌ |
| درگاه پرداخت | بدونش «مشتری واریز کرد» اتفاق نمی‌افتد | ❌ |
| حساب/کلیدِ تأمین‌کننده‌ها | برای خریدِ خودکار | ❌ |
| کیف پول تتر با موجودی | برای خریدِ خودکار | ❌ |

⚠ **مهم‌ترین نکته‌ی این سند:** بخش ۴ (خریدِ خودکار) با پولِ واقعی
کار می‌کند. تا وقتی این پنج‌تا آماده نیست، آن بخش فقط تا مرزِ
«صف و شبیه‌سازی» ساخته می‌شود و دکمه‌ی اجرای واقعی‌اش خاموش
می‌ماند.

## ۱ — نرخ تتر از چند منبع

**خواسته:** قیمت را از تتر بگیرد، از چند جا نه یکی، کمترین را
انتخاب کند، به تومان تبدیل کند و مبلغی که ما می‌کشیم رویش جمع
شود.

**ساختار:**

```
wp-plugin/phoenix-bridge/includes/
  rate-sources.php     ← تعریف منابع (نام، آدرس، مسیرِ عدد، واحد)
  rate.php             ← جمع‌آوری، انتخاب، کش، اندپوینت  [هست، باید بازنویسی شود]
```

منابع پیشنهادی (همه بدون کلید، همه باید تأیید شوند):
`nobitex` · `wallex` · `bitpin` · `ramzinex` · `tgju`

منطق:

1. هر منبع با تایم‌اوت ۵ ثانیه، **موازی نه پشت‌سرهم**
2. هر عددی که بیرونِ بازه‌ی معقول باشد دور ریخته می‌شود
   (بازه از میانه‌ی همان دور ساخته می‌شود، نه عددِ ثابت)
3. اگر کمتر از **دو** منبع جواب داد → نرخِ قبلی می‌ماند و هشدار
   ثبت می‌شود. با یک منبع تصمیم نمی‌گیریم.
4. **کمترین** عدد انتخاب می‌شود
5. قیمت نهایی = `کمترین نرخ × مبلغ دلاری × (۱ + حاشیه)`

⚠ دو نکته که باید سرِ ساخت حواسمان باشد:

- **ریال یا تومان.** بیشترِ منابعِ ایرانی ریال می‌دهند. یک بار
  تقسیم بر ده جا بیفتد، قیمتِ کلِ فروشگاه ده برابر می‌شود. هر
  منبع واحدش صریح نوشته شود.
- **کمترین نرخ یعنی کمترین قیمتِ فروش.** اگر یک منبع خراب شود و
  عددِ نصف بدهد، ما ارزان‌تر از قیمتِ تمام‌شده می‌فروشیم. برای
  همین شرطِ «حداقل دو منبع» و بازه‌ی معقول، نه تزئین است نه
  احتیاطِ اضافه.

**حاشیه‌ی سود** سه جا قابل تعریف: پیش‌فرضِ کل، به‌ازای دسته، و
به‌ازای محصول. هرچه خاص‌تر، برنده.

## ۲ — تازه‌سازی: ساعتی + سرِ هر خرید

| کِی | با چه | نکته |
|---|---|---|
| هر ساعت | `wp_cron` رویداد `phoenix_rate_refresh` | کرونِ وردپرس با بازدید اجرا می‌شود؛ روی سایتِ کم‌بازدید تأخیر دارد → با cron واقعیِ سرور جایگزین شود |
| سرِ هر خرید | هوک `woocommerce_checkout_order_processed` | فقط وقتی نرخ کهنه‌تر از ۵ دقیقه باشد |
| دستی | دکمه‌ی «به‌روزرسانی الان» در پنل | با nonce و محدودیتِ دفعات |

⚠ **قیمتِ لحظه‌ی پرداخت قفل می‌شود.** نرخ بعد از افزودن به سبد
عوض می‌شود؛ اگر قیمت بینِ سبد و پرداخت بالا برود و ما بی‌خبر
عوضش کنیم، مشتری حق دارد شاکی باشد. قیمت سرِ ثبتِ سفارش روی
همان سفارش ذخیره می‌شود و دیگر تکان نمی‌خورد.

## ۳ — پنل وردپرس

`wp-plugin/phoenix-bridge/includes/admin-pricing.php`

⚠ **قاعده‌ی این پنل، به خواسته‌ی کارفرما: هر چیزی که خودکار است
باید دستی هم بشود، و هر وضعیتی باید دیده شود.**

یعنی هیچ کاری پشتِ پرده اتفاق نمی‌افتد که ادمین نتواند ببیندش،
جلویش را بگیرد، یا خودش انجامش دهد. هر صفحه سه چیز دارد:
**وضعیتِ الان**، **تاریخچه**، و **دکمه‌ی دستی**.

منوی «فونیکس» با پنج زیرصفحه:

### ۳.۱ داشبورد

یک نگاه، کلِ وضعیت:

- نرخِ فعلی، از کدام منبع، چند دقیقه پیش
- وضعیت هر منبع — سبز/زرد/قرمز با آخرین زمانِ پاسخ
- کارهای امروز: چند سفارش، چند تحویلِ خودکار، چند شکست
- تخفیف‌های فعال و زمانِ پایانشان
- هشدارها: منبعِ از کار افتاده، صفِ گیرکرده، نرخِ کهنه

### ۳.۲ نرخ

- جدولِ زنده‌ی همه‌ی منابع: نام، عدد، واحد، زمانِ پاسخ، وضعیت
- کدام برنده شد و **چرا** (کمترین؟ یا بقیه رد شدند؟)
- نمودارِ نرخ در ۲۴ ساعت و ۷ روزِ گذشته
- دکمه‌ی «به‌روزرسانی الان»
- **نرخِ دستی** — پر که شود همه‌ی منابع نادیده گرفته می‌شوند،
  با تاریخِ انقضا تا یادمان نرود برداریمش
- روشن/خاموش کردنِ تک‌تکِ منابع
- تاریخچه‌ی کاملِ تغییرات: چه کسی، کِی، از چند به چند

### ۳.۳ حاشیه‌ها

- حاشیه‌ی پیش‌فرضِ کل
- جدولِ حاشیه به‌ازای دسته
- جدولِ حاشیه به‌ازای محصول (با جست‌وجو)
- **پیش‌نمایشِ زنده**: پیش از ذخیره نشان می‌دهد قیمتِ ده محصولِ
  پرفروش از چند به چند می‌رسد
- قفلِ قیمت روی یک محصول: «این یکی دستی است، به نرخ کار نداشته باش»

## ۴ — خریدِ خودکار بعد از پرداخت

**خواسته:** وقتی مشتری واریز کرد، خودش برود بخرد و روی اکانتِ
مشتری فعال کند.

**ساختار:**

```
includes/fulfil/
  queue.php              ← جدولِ کار، وضعیت، تلاشِ دوباره
  provider.php           ← رابطِ مشترکِ تأمین‌کننده
  provider-manual.php    ← پیش‌فرض: کار می‌رود به صفِ دستی
```

جریان: `پرداخت تأیید شد → کار ساخته می‌شود → اجرا → ثبتِ نتیجه`

⚠ **این بخش پیش‌فرض خاموش ساخته می‌شود، و این یک تصمیمِ عمدی
است.**

سه دلیل:

1. **پولِ واقعی.** یک حلقه‌ی خراب، به‌جای یک خرید صد خرید
   می‌کند. هر کار باید کلیدِ یکتا داشته باشد تا دوبار اجرا نشود.
2. **تأمین‌کننده هنوز معلوم نیست.** بدون API واقعی، هر کدی که
   بنویسم حدس است.
3. **سقف لازم دارد.** سقفِ روزانه‌ی ریالی، سقفِ تعداد، و توقفِ
   خودکار وقتی چند کارِ پشتِ‌سرهم شکست خورد.

پیشنهاد: اول با **تأییدِ دستی** راه بیفتد — سفارش می‌آید، پنل
می‌گوید «این را بخرم؟»، اپراتور تأیید می‌کند. بعد از یکی‌دو ماه
که آمار داشتیم، خودکار شود.

## ۵ — تخفیف‌ها

**خواسته:** گروهی روی یک دسته، روی همه، روی یک تگ، تکی، و کدِ
اختصاصی برای یک نفر.

ووکامرس کوپن دارد ولی «۲۰٪ روی کلِ دسته‌ی گیم تا جمعه» را ساده
نمی‌کند. پس:

```
includes/discounts.php
```

یک قاعده = `{ دامنه, هدف, نوع, مقدار, از, تا, سقف }`

- **دامنه:** همه | دسته | تگ | محصول
- **نوع:** درصدی | مبلغ ثابت
- **سقف:** برای درصدی — «۲۰٪ ولی حداکثر ۵۰۰ هزار»

**کدِ اختصاصی برای یک نفر:** همان کوپنِ ووکامرس با
`usage_limit = 1` و قفل روی شماره‌ی موبایل. ساختنش از پنل، یک
دکمه.

⚠ **قاعده‌ی جمع‌نشدن.** اگر سه تخفیف روی یک محصول بیفتند،
پیش‌فرض این است که **بهترین یکی** اعمال شود نه هر سه. بدونِ این،
یک شبِ جمعه محصول رایگان می‌شود.

---

## ۶ — امنیت و رفتار سرِ حمله

هر چیزی که در بخش‌های بالا نوشته می‌شود، این‌ها را دارد:

| خطر | کاری که می‌کنیم |
|---|---|
| نوشتن بدون اجازه | `current_user_can('manage_woocommerce')` روی هر نوشتن |
| CSRF | `wp_nonce` روی هر فرم و هر REST نوشتنی |
| تزریق | `$wpdb->prepare` همه‌جا، `sanitize_*` روی هر ورودی |
| XSS در پنل | `esc_html` / `esc_attr` روی هر خروجی |
| لو رفتن کلید | هیچ کلیدی در جاوااسکریپت — همه در `wp-config.php` |
| DoS روی اندپوینت نرخ | کش، و سقفِ درخواست بر IP |
| منبعِ دروغ‌گو | حداقل دو منبع + بازه‌ی معقول (بخش ۱) |
| خریدِ تکراری | کلیدِ یکتا روی هر کار (بخش ۴) |
| منبع از کار افتاد | نرخِ قبلی + هشدار، نه قیمتِ صفر |
| پایگاه‌داده قفل شد | کار در صف می‌ماند، بعداً دوباره اجرا می‌شود |

**تست‌ها:** هر بخش با تستِ واحد برای منطقِ انتخابِ نرخ و برخوردِ
تخفیف‌ها، به‌علاوه‌ی یک اجرای دستی روی نصبِ آزمایشی.
